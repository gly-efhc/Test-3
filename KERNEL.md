## 1. Назначение и разделение полномочий

`gly-efhc/efhc` хранит открытый код frontend, необходимые ресурсы, тесты, CI, публично безопасный onboarding. Приватный [efhc_archive](https://github.com/gly-efhc/efhc_archive) хранит закрытую документальную историю, решения OWNER, CANON, SSOT, NORM, REPORTS и CYCLES. Утверждённый физический локальный ZIP Архива и его удалённая Git-копия имеют независимые идентификаторы: утверждение локального файла само по себе не означает успешного удалённого импорта. Реальное исполнение кода и результат CI подтверждают только соответствующие `CODE_HEAD` и job/artifact.

Нет автоматической транзакции между efhc, private Архивом и backend. Фиксировать их SHA по отдельности и сверять перед записью. Не объявлять старый зафиксированный SHA текущим после новых коммитов.

## 2. Первое чтение и маршрутизация

`AGENTS → START_HERE → KERNEL (once) → INDEX → exact CODE_HEAD → authenticated private archive (if dependency) → thematic canon/SSOT → scoped source → verification → readback`.

Для приватного репозитория **единственно разрешённый путь — авторизованный GitHub-коннектор**. Запрещены public web, GitHub через браузер, Browser Use/Cloud Browser, raw HTTP и обходы при отсутствии доступа. Публичные URL private документов — указатели, а не доказательство чтения. При отсутствии разрешённого коннектора ставить `PRIVATE_DEPENDENCY_BLOCKED`; не продолжать зависящую от приватных норм кодовую запись.

После входа в private архив: его `AGENTS.md`, `START_HERE.md`, `KERNEL.md` один раз, `INDEX.md`, `01_CANON/TERMS.md`, `17_CONTROL/DOCUMENT_MANAGEMENT_RULES.md`; затем только относящиеся к задаче CANON/SSOT/NORM/OWNER decisions. Старые маршруты разрешать через private `17_CONTROL/HISTORY_PATH_RESOLVER.md`, не копировать историю в public.

## 3. Режим исполнения и необходимость согласования

- `AUDIT_READ_ONLY`: анализ, трассировка, сравнение, без записи, deploy, публикации или нового номера отчёта.
- `CODE_WRITE_APPROVED`: только прямо разрешённые файлы efhc. Доступ к репозиторию не заменяет разрешения менять бизнес-логику, стили, tests, workflows.
- `RELEASE_DEPLOY_APPROVED`: отдельная релизная операция; нужен проверенный физический source, CI, artifact, readback и разрешённый канал публикации.
- `PRIVATE_DOC_WRITE`: только по отдельному распоряжению OWNER, только в приватный Архив через разрешённый коннектор; не следует из права записи efhc.

Если есть конфликт источников, защищённых accepted состояний, неясный разрушительный scope или конкурирующий агент — прекратить только зависимое изменение и задать короткий предметный вопрос. Не дублировать уже отвеченные OWNER вопросы. Утверждённое решение не открывать повторно без новых обстоятельств.

## 6. Алгоритм изменения кода и CI

Обязательная граница именования: [NO_WORK_PREFIXES — решение OWNER](https://github.com/gly-efhc/efhc_archive/blob/main/01_CANON/OWNER_DECISIONS.md#no_work_prefixes). Не создавать технические идентичности файлов, CSS-классов, DOM-атрибутов, функций и переменных с номерами версий/циклов/итераций; использовать функциональные имена. [Блокирующий Guard](site/ci/work-prefixes.md) обязателен до публикации; PASS не заменяет активный Ruleset. Старые имена очищать только вместе с проверенными потребителями, сохраняя принятые страницы, тесты и эталоны.

1. `PIN`: проверить текущий Git HEAD, зависимости, разрешённые файлы, ссылки на SSOT.
2. `SCOPE`: установить контракт наблюдаемого поведения и защищённые поверхности.
3. `EDIT`: минимальные изменения только по маршруту; не добавлять избыточный framework или дублирующий runtime.
4. `VERIFY`: при необходимости `npm ci`, `npm run typecheck`, `npm run test:frontend-regression`, targeted parity, `npm run build` из `site/frontend/`; эти проверки выбирать по изменённому scope, а не объявлять выполненными заранее.
5. `PUBLISH`: контролируемый commit/PR, без force и несанкционированного deploy.
6. `READBACK`: remote HEAD + file content + фактические job conclusions; указывать отрицательные проверки, непроверенные ветки и OWNER visual acceptance отдельно.

Документационные изменения не требуют фиктивного запуска Next.js. Релизный ZIP является отдельной физической копией: сравнивать tree, checksums, manifest и отграничивать public code от private docs.
